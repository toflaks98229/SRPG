## 3. 어셈블리 계층

의존은 **한 방향으로만** 흐른다. 아래 계층이 위 계층을 참조하는 일은 없다.

```
SRPG.Common          (공용 타입 · 인터페이스 · 상수. 의존 없음)
   ↑
SRPG.Data            (ScriptableObject 정의, 세이브 데이터 스키마)
   ↑
SRPG.Core            (부트스트랩, DI, 이벤트 버스, 매니저, 세이브, 상태머신)
   ↑
SRPG.Systems         (AI · 패스파인딩 · 전투 · 진형 · 시야 · 스탯 — 순수 시스템)
   ↑
SRPG.Gameplay        (유닛 · 분대 · 명령 · 카메라 · 섬 · 캠페인 — 게임 객체)
   ↑
SRPG.UI              (HUD · 컨트롤러 · 위젯 · 월드스페이스 UI)
   ↑
SRPG.Composition     (전 계층을 엮는 조립 지점. 여기서만 전부를 안다)

SRPG.Editor          (Editor 전용. 전 계층 참조)
SRPG.Tests.EditMode  / SRPG.Tests.PlayMode
```

**왜 이렇게 나누는가**: `Systems`가 `Gameplay`를 모르기 때문에, AI·패스파인딩 로직을 게임 객체 없이 EditMode 테스트로 검증할 수 있다. 전투 AI가 핵심인 프로젝트에서 이 분리는 선택이 아니라 필수다.

**`SRPG.Framework` 는 없앴다**: 풀링·입력·시간·수학·디버그를 담을 자리로 잡아 두었지만 파일이 한 개도 들어오지 않았다. 계획한 것들은 전부 다른 곳에서 제 주인을 찾았다 — 투사체 풀은 전투 컨텍스트가, 시간은 `TacticalTimeController` 가, 수학은 `Systems` 의 각 솔버가 들고 있다. 빈 어셈블리는 컴파일 단위와 참조 그래프에 계속 남아 있으면서 아무것도 하지 않으므로, 자리만 잡아 두는 대신 필요해질 때 만들기로 한다.

## 5. 현재 asmdef 참조 상태 (중요)

**현재 asmdef는 SRPG 프로젝트에 실제로 설치된 패키지만 참조한다.** 미설치 어셈블리를 참조하면 Unity가 매 컴파일마다 오류를 내기 때문이다.

현재 참조 중:
`VContainer`, `Unity.TextMeshPro`, `UnityEngine.UI`, `Unity.InputSystem`, `Unity.AI.Navigation`,
`Unity.RenderPipelines.Core.Runtime`, `Unity.RenderPipelines.Universal.Runtime` (Gameplay/UI/Composition/Editor만)

**`VContainer` 는 `Core` 이상만 참조한다.** `Common` 과 `Data` 는 참조하지 않는다 — 그 두 계층은 순수 타입이라 컨테이너를 알 이유가 없고, 알게 두면 언젠가 `[Inject]` 가 붙는다.

### 5.1 도입 검토가 필요한 패키지

SCPPJ는 아래를 쓰고 있으나 SRPG에는 아직 없다. **패키지 설치는 프로젝트 전반에 영향을 주므로 별도 결정 사항으로 남겨둔다.**

| 패키지 | 매니페스트 항목 | 용도 | 우선도 |
|---|---|---|---|
| Mathematics | `"com.unity.mathematics"` | 벡터·곡선 연산, Job 호환 | 중간 |
| Collections | `"com.unity.collections"` | 영향력 맵·플로우 필드 네이티브 배열 | 중간 |
| Burst | `"com.unity.burst"` | AI/패스파인딩 성능 | 중간 |
| Addressables | `"com.unity.addressables": "2.9.1"` | 에셋 로딩 | 중간 |
| Unity Behavior | `"com.unity.behavior": "1.0.16"` | BT 그래프 저작 (`08.Behavior/`) | 낮음 |
| Splines | `"com.unity.splines": "2.9.0"` | 경로·연출 | 낮음 |

도입 시 각 asmdef의 `references` 배열에 해당 어셈블리명을 추가해야 한다.

**VContainer 는 2026-08-11에 들어왔다**(커밋 `7cab00f`). 수명을 전역·캠페인·전투 셋으로 가르는 구조가 그 위에 서 있다. `Collections` · `Burst` 의 우선도가 "높음"에서 내려간 것은, 실측한 병목이 알고리즘 복잡도가 아니라 **프레임당 관리 호출 수와 불필요한 재계산**이었기 때문이다. `InfluenceMap` · `GridPathfinder` · `BallisticSolver` 가 전부 순수 클래스라 필요해진 시점에 옮기면 호출부를 고칠 일이 거의 없다.

## 6. 코딩 규약

루트에 `.editorconfig`를 SCPPJ에서 그대로 가져왔다. 요점:

- 기본 인코딩 **UTF-8**, 줄바꿈 **CRLF**, 들여쓰기 **스페이스 4칸**
- `.cs` / 셰이더 → **UTF-8 with BOM**
  이유: Unity·Visual Studio가 BOM 없이는 한글 주석을 CP949로 오인해 저장하는 사고가 있다.
- `.json` / `.csv` / `.md` 등 데이터 파일 → **BOM 없는 UTF-8**, 들여쓰기 2칸
  이유: CSV 임포터 같은 커스텀 파서가 BOM을 첫 컬럼 값으로 읽는 사고 방지.
- Unity 직렬화 YAML(`.unity`, `.prefab`, `.asset`, `.meta` 등) → Unity가 쓰는 형식 그대로 둔다.

### 6.1 인코딩은 테스트가 지킨다

`.editorconfig`는 편집기에게 **부탁**할 뿐 강제하지 못한다. 실제로 2026-08-12 이전에는 `.cs` 181개 중 **BOM 이 있는 것이 40개뿐**이었다. BOM 없는 UTF-8 도 유효한 UTF-8 이라 컴파일이 통과하므로, 어긋난 상태가 스스로 드러나지 않는다.

**같은 날 191개(`.cs` 181 · `.shader` 7 · `.hlsl` 3)를 UTF-8 BOM + CRLF 로 통일하고, `SourceEncodingTests` 를 붙였다.** 이제 규약을 어기면 EditMode 검사가 빨간불을 켠다. 자세한 경위는 전투 프로토타입 문서 §7.7 에 있다.

| 검사 | 무엇을 막는가 |
|---|---|
| 소스에 BOM 이 있는가 | 한글 주석이 CP949 로 오인돼 깨지는 사고 |
| 데이터 파일에 BOM 이 없는가 | CSV 파서가 BOM 을 첫 컬럼 값으로 읽는 사고 |
| 전부 올바른 UTF-8 인가 | BOM 은 붙어 있는데 본문이 이미 깨진 상태 |

**줄바꿈은 검사하지 않는다.** `.gitattributes` 가 커밋 시 정규화하므로 작업 트리의 줄바꿈은 플랫폼마다 다르고, 리눅스 검사 서버는 LF 를 본다. 거기서 CRLF 를 요구하면 고칠 수 없는 실패가 된다. BOM 을 검사하는 이유가 정확히 그 반대다 — **git 이 손대 주지 않기 때문**이다.

#### 검사가 실패하면

BOM 을 붙이는(또는 떼는) 일괄 처리다. 읽을 때 BOM 을 자동 감지해 벗겨 내고, 쓸 때 원하는 형태로 다시 붙인다.

```powershell
$bom = New-Object System.Text.UTF8Encoding($true)   # $false 면 BOM 없이
Get-ChildItem Assets\_Project -Recurse -Include *.cs,*.shader,*.hlsl | ForEach-Object {
  $t = [IO.File]::ReadAllText($_.FullName)
  $t = ($t -replace "`r`n", "`n") -replace "`n", "`r`n"
  [IO.File]::WriteAllText($_.FullName, $t, $bom)
}
```

**일괄 처리는 다른 변경이 없는 커밋으로 따로 한다.** 191개가 한꺼번에 수정된 것으로 잡히므로, 다른 변경을 섞으면 그 커밋에서 무엇이 실제 변경인지 읽을 수 없게 된다.

#### 인코딩을 잴 때의 함정

**`git show HEAD:파일 > 임시파일` 로 재면 안 된다.** PowerShell 의 `>` 가 출력을 BOM 포함 UTF-8 로 다시 인코딩해서, **원본에 BOM 이 없어도 있는 것으로 나온다.** 실제로 이 측정을 믿고 BOM 없던 파일 10개에 BOM 을 잘못 붙인 적이 있다.

| | 방법 | 안전한가 |
|---|---|---|
| 작업 트리 | `[IO.File]::ReadAllBytes($path)` | 예 |
| 커밋된 내용 | `git cat-file blob <sha> \| head -c 3 \| od -An -tx1` | 예 |
| 커밋된 내용 | `git show HEAD:path > tmp` 후 읽기 | **아니오** |

일반화하면 — **측정 도구가 측정 대상을 바꾸지 않는지 먼저 의심할 것.** 인코딩·줄바꿈·공백처럼 눈에 보이지 않는 것을 잴 때는 셸 리다이렉션과 복사·붙여넣기가 전부 값을 바꾼다.

`.gitignore` / `.gitattributes`도 함께 복사했다. **저장소는 2026-08-07에 열렸다**(첫 커밋 `5615f0a`). 주 브랜치는 `main` 이다.

### 6.2 XML 문서 주석은 컴파일러가 검사한다

루트의 `Directory.Build.props` / `Directory.Build.targets` 가 `GenerateDocumentationFile` 을 켠다. 리팩터링 중 멤버를 옮기면 주석 블록이 **엉뚱한 멤버에 붙는** 사고가 나는데(실제로 두 번 났다), 그것이 `CS1573`·`CS1572`·`CS1574` 로 드러난다. 특히 `CS1574` 는 **어셈블리 경계를 넘는 `cref`** 를 잡는다 — `SRPG.Gameplay` 가 `SRPG.Composition` 의 타입을 `cref` 로 걸면 여기서 걸린다.

`CS1591`(공개 멤버에 문서 주석 없음)은 끈다. 문서는 쓸 값어치가 있는 곳에만 쓴다.

**유니티 에디터 콘솔에는 나오지 않는다.** 유니티는 자체 파이프라인으로 컴파일하므로, 확인하려면 명령줄에서 직접 빌드해야 한다.

```bash
dotnet build SRPG.slnx
```

## 7. 빈 폴더 유지

git은 빈 디렉터리를 추적하지 않으므로 모든 빈 폴더에 `.gitkeep`을 넣어두었다. 해당 폴더에 실제 파일이 생기면 `.gitkeep`은 지워도 된다.
