## 1-1. 씬 구성과 에셋

### 씬 계층 (`Battle.unity`)

```
Environment
├── BattleCamera        Camera + BattleCameraRig + AudioListener
└── DirectionalLight    방향광 (그림자 Soft)
BattleBootstrap         BattleSetup_Prototype 참조, 카메라·Runtime 루트 연결
Runtime                 (비어 있음 — 재생하면 여기에 생성물이 채워집니다)
```

씬에 배치하는 것은 **런타임에 만들 수 없거나 만들면 손해인 것**으로 한정했습니다. 카메라·조명·환경광은 씬 에셋에 저장되어야 하고, 부트스트랩은 기획자가 인스펙터에서 만져야 합니다. 지형·유닛·상륙정은 절차적으로 만들어지므로 씬에 넣지 않습니다.

환경광은 `AmbientMode.Trilight`로 설정했습니다. 기본 스카이박스를 그대로 두면 절벽 그늘이 새까맣게 죽어 지형 판독이 어려워집니다.

### 생성되는 에셋

| 위치 | 내용 |
|---|---|
| `04.Art/03.Shaders/Materials/` | 머티리얼 18종 (지형 5, 아군 4, 적 3, 소품 4, 마커 2) |
| `05.Prefabs/Units/` | `Unit_Militia` `Unit_Infantry` `Unit_Archer` `Unit_Pike` |

### 유닛 프리팹 구조

```
Unit_Infantry
├── Unit (컴포넌트)  _commanderFlag → CommanderFlag, _bodyRenderer → Body
├── Body             캡슐 메시 + 병과 머티리얼
└── CommanderFlag    ★ 비활성 상태로 저장
    ├── Pole
    └── Cloth
```

**병사와 지휘관의 프리팹을 나누지 않습니다.** 한 프리팹 안에 깃발을 꺼 둔 채 넣고 `Unit.Initialize(isCommander)`가 켭니다. 프리팹이 두 벌이면 구조나 밸런스를 고칠 때 한쪽만 고치는 사고가 반드시 납니다.

### 에셋이 없어도 실행됩니다

`BattleSetup`의 모든 필드는 비워 둘 수 있고, 비면 부트스트랩이 코드 기본값과 프리미티브로 대체합니다. 두 가지 이유입니다 — 클론 직후 재생 버튼만으로 게임이 보여야 하고, PlayMode 테스트가 에셋 없이 돌아야 합니다.

> **주의**: 폴백이 있다는 건 **참조가 끊겨도 조용히 돌아간다**는 뜻입니다. 실제로 이 함정에 한 번 빠졌습니다(§7 참조). 그래서 `PrototypeAssetBuilder`가 마지막에 `VerifyReferences()`로 참조를 스스로 검사하고 콘솔에 결과를 찍습니다. **"참조 검증 통과" 로그가 안 보이면 폴백으로 돌고 있는 것입니다.**

## 2. 무엇이 구현되었는가

### 2.1 절차적 섬 생성 — `Systems/Grid/IslandGenerator.cs`

```
1) 반경 + 펄린 노이즈로 윤곽 결정 → 격자 테두리는 강제로 바다
2) 가장 큰 연결 덩어리만 남김 (고립된 조각 제거)
3) 바다로부터의 거리(다중 소스 BFS)로 계단식 고도 부여
4) 고지대에 바위 배치 → 초크포인트 생성 (섬을 단절시키면 되돌림)
5) 내륙 평지에 가옥 배치 (최소 간격 유지)
6) 해안을 각도로 나눠 상륙 구역 생성
```

**설계상 중요한 두 가지**

- **바위 배치 시 연결성을 매번 검사합니다.** 섬이 두 조각으로 갈라지면 분대가 닿을 수 없는 영역이 생겨 방어가 성립하지 않습니다. `IsConnected` 검사에 걸리면 그 바위를 취소합니다.
- **상륙 구역을 각도로 나눕니다.** 해안 타일을 섬 중심 기준 각도로 정렬해 K개 구간으로 자르면, 구역들이 둘레에 고르게 흩어집니다. 이게 전선 분산 압박의 출발점입니다.

고도는 해안 거리에서 유도하므로 **인접 타일의 고도차가 항상 1 이하**로 보장됩니다. 경로 탐색이 고도차 2 이상을 막기 때문에, 이 성질이 깨지면 통행 불가 구역이 생깁니다. EditMode 테스트로 못 박아 두었습니다.

### 2.2 적 스폰 — `Gameplay/Enemies/`

```
WaveScheduler (Systems/Spawning, 순수 타이머)
   └→ EnemySpawner : 상륙 구역을 섞어서 배 배치
         └→ EnemyShip : 먼바다 → 해안 접근 → 병력 하선 → 퇴각
               └→ Unit + EnemyAgent : 목표 선정 → A* → 경로 추종
```

- **상륙정을 별도 액터로 둔 이유**: ① 접근 과정 자체가 "어느 해안이 위험한지"의 예고가 됩니다 (Into the Breach식 텔레그래핑을 실시간에 옮긴 것) ② 궁수가 상륙 전 배 위의 적을 때릴 수 있어야 병과 역할이 성립합니다.
- **매 웨이브 상륙 구역을 섞습니다.** 같은 해안만 노리면 방어가 너무 쉬워집니다.
- `WaveScheduler`는 **스케일된 시간**으로 진행합니다. 슬로우모션 중에도 웨이브가 밀려오지 않으면 명령 입력이 곧 시간 벌기가 되어 버립니다.

### 2.3 분대 시스템 — `Gameplay/Squads/Squad.cs`

**앵커 구조**

```
분대는 "앵커" 한 점만 A* 경로를 따라 이동
   └→ 병사들은 앵커 또는 진형 슬롯을 향해 조향 (Arrive + Separation)
```

유닛마다 경로를 계산하지 않으므로 비용이 **분대 수**에 비례합니다. 유닛 수에 비례하지 않습니다.

**진형은 도착한 뒤에만 잡습니다**

| 상태 | 병사가 향하는 곳 |
|---|---|
| 이동 중 | **전원이 앵커 한 점** — 슬롯 없음. 분리 조향이 퍼뜨려 느슨한 무리가 됨 |
| 도착 후 | `SolveRings` 동심원 슬롯. **방향 없음** |

이동 중에 진형을 유지시키면 두 가지가 망가집니다 — 뒤쪽 병사가 앞쪽 자리를 맞추느라 옆걸음질하며 행군이 느려지고, 진형 방향이 계속 회전해 병사들이 제자리에서 도는 것처럼 보입니다. 실제로 병력이 대열을 갖추는 것은 자리를 잡고 난 다음입니다.

**진형에 방향이 없는 이유**도 두 가지입니다 — 실시간에서 위협은 사방에서 오므로 한 방향으로 전열을 세우면 나머지 세 방향이 항상 약점이 되고, 방향이 없으면 회전으로 인한 부자연스러움 자체가 사라집니다.

**이중 손실 구조 (조사 보고서 2.5절)**

| 손실 | 결과 |
|---|---|
| 병사 사망 | 분대 유지. 인원만 줄어듦 |
| **지휘관 사망** | **분대 전체 영구 소멸** |

지휘관은 동심원의 **중심(슬롯 0번)** 에 섭니다. 방향이 없는 진형에서 사방으로부터 가장 안쪽이 곧 가장 안전한 자리입니다.

**분대 랭크**(`Rank`, 1~5)는 소속 병사 전원이 공유합니다. 현재는 **궁수의 조준 산포**가 이 값에 직접 좌우됩니다(§2.7). 업그레이드 시스템이 붙을 자리입니다.

### 2.4 유닛 전투 판단 — `Gameplay/Units/Unit.cs`

플레이어는 "이동"만 지시하므로, 나머지 판단은 전부 여기서 일어납니다.

```
· 슬롯에서 멀면      → 이동 우선
· 슬롯 근처 + 사거리 내 → 멈춰서 공격
· 슬롯 근처 + 사거리 밖 → 리시(2.8) 범위 안에서만 접근
· CanAttackWhileMoving = false (창병) → 이동 중 공격 금지
```

`Unit`은 **공격을 시작할지만** 정합니다. 누가 맞는지는 무기가 물리 질의로 판정합니다(§2.6).

### 2.5 시간 제어 — `Systems/Time/TacticalTimeController.cs`

`Time.timeScale`이 0.15로 부드럽게 내려갑니다. **완전 정지가 아닌 이유**는 조사 보고서 5.1절 — 완전 정지는 최적해 탐색을 유도해 사실상 턴제가 됩니다.

**슬로우모션은 "분대를 골랐고 아직 명령을 안 내린" 동안에만 걸립니다.** 선택 상태만으로 판단하면 명령 후에도 시간이 느려진 채 남아, 아무것도 선택하지 않는 것이 가장 유리한 플레이가 되어 버립니다. 명령을 내리는 순간 시간이 돌아와야 결정의 결과를 제 속도로 마주하게 됩니다.

**주의사항**이 코드에 반영되어 있습니다:
- 카메라와 시간 보간은 `unscaledDeltaTime` (슬로우모션 중에도 조작감 유지)
- 웨이브 진행은 `deltaTime` (슬로우모션이 이득이 되지 않게)
- `OnDestroy`에서 `Reset()` 호출 (다음 씬이 느려진 채 시작하지 않게)

배율 0.15는 `BattleTuning.SlowMotionScale`입니다. §6에서 "너무 느리거나 빠르지 않은가"를 검증 항목으로 올려 두었는데, 값이 `private const`로 박혀 있으면 확인할 때마다 재컴파일이 필요합니다. 검증하겠다고 적어 둔 것은 인스펙터에서 만질 수 있어야 합니다.

### 2.5-1 튜닝 수치 — `Data/Configs/BattleTuning.cs`

**기준은 하나입니다. 기획자가 게임의 감각이나 밸런스를 바꾸려고 만질 값인가.** 그렇다면 데이터고, 아니면 코드 상수로 남습니다. (`SlotArrivalThreshold = 0.45` 같은 구현 세부는 옮기지 않았습니다)

| 항목 | 기본값 | 무엇이 바뀌는가 |
|---|---|---|
| `SlowMotionScale` / `SlowMotionTransitionSpeed` | 0.15 / 8 | 명령 입력의 여유와 전환 이질감 |
| `FormationSpacing` / `AnchorSpeedFactor` | 0.95 / 0.92 | 분대 밀집도 → 궁수 광역 효율, 행군 대열 길이 |
| `ChaseLeash` | 2.8 | 진형 유지 ↔ 눈앞의 적 추격 |
| `EnemyAggroRadius` / `EnemyRepathInterval` | 11 / 0.9 | 적 AI 공격성, 반응 속도 ↔ 경로 탐색 비용 |
| `ShipSpeed` / `ShipUnloadInterval` | 4.2 / 0.35 | 상륙 예고 유예, 웨이브 압박 강도 |
| `ShieldSteepBlockMarginDegrees` | 11 | 고지대 사격의 방패 관통 여부 (§2.7) |

에셋을 비워 두어도 됩니다. 부트스트랩이 `CreateDefault()`로 대체하며 값은 위 표와 같습니다. `BattleContext.Tuning`은 **절대 null이 아니므로** 소비자는 검사하지 않습니다.

### 2.6 물리 기반 전투 — `Gameplay/Weapons/`

피해를 "사거리 안이면 즉시 적용"에서 **"무기가 실제로 닿은 곳에서 적용"** 으로 바꿨습니다. 그래서 공격은 순간이 아니라 **시간을 갖는 동작**이 되고, 준비 → 판정 → 회수 세 구간으로 나뉩니다. 판정 구간에서만 물리 질의를 돌립니다.

| 무기 | 판정 형상 | 특성 |
|---|---|---|
| `MeleeWeapon` (검) | 칼날이 훑은 자리를 캡슐로 스윕 | 호 밖은 안 맞음 / 여럿 동시 타격 / 휘두르는 중 들어온 적도 맞음 |
| `PikeWeapon` (창) | 앞으로 뻗은 자루 선분 + **정면 42° 원뿔** | 사거리 우위가 자루 길이(2.1)에서 물리적으로 나옴. **측면·후방이 빔** |
| `BowWeapon` (활) | 화살을 실제로 발사 | 예측 조준 → 탄도 → 산포 |

**창이 별도 오브젝트로 그려지는 이유**는 단순한 장식이 아닙니다. 적이 창끝에 닿기 전에 먼저 맞는 것이 눈에 보여야, 왜 창병 앞으로 걸어 들어가면 안 되는지가 전달됩니다. 그리고 정면 원뿔 판정 때문에 측면이 비므로, 조사에서 확인한 **"이동하거나 측면을 잡히면 창병 대열이 무너진다"** 가 규칙이 아니라 형상에서 나옵니다.

**넉백과 익사**가 전투의 핵심입니다. 조사에서 확인한 대로 Bad North에서 **물에 빠지면 즉사**하고, 강한 넉백이 유닛을 물로 밀어냅니다. 구현에서도 평상시엔 물가에서 멈추지만 **넉백 중에는 물 위로 밀려나 익사**합니다. 이 예외가 없으면 넉백은 그냥 밀치기 연출이 되고 물이 위험 요소가 되지 않습니다.

### 2.7 화살 — 곡사 · `Gameplay/Weapons/Arrow.cs`, `Systems/Combat/BallisticSolver.cs`

궁수는 피해를 전달하지 않습니다. **화살을 쏘고, 그 화살이 맞으면 피해가 납니다.** 그래서 규칙 없이 다음이 성립합니다.

- 빗나감 (그리고 빗나간 화살이 뒤의 다른 적에게 맞음)
- 아군이나 지형이 사선을 막으면 못 맞힘
- 날아가는 동안 대상이 움직이면 놓침 → **그래서 예측 사격이 필요해짐**

#### 곡사 — 속력이 아니라 발사각을 고정한다

**`useHighArc: true`를 쓰지 않습니다.** 속력을 고정하고 각을 푸는 방식에서 높은 궤도 해를 고르면, 사거리에 비해 속력이 과할 때 발사각이 수직에 수렴합니다. 22 m/s로 9 m 앞을 쏘면 **약 85°** — 화살이 하늘로 솟았다 떨어집니다.

그래서 반대로 풉니다. 발사각(40°)을 고정하고 거리에 맞는 속력을 계산합니다.

$$v^2 = \frac{g\,x^2}{2\cos^2\theta\,(x\tan\theta - y)}$$

어떤 거리에서도 **포물선 모양이 일정**하고 속력만 변합니다. 분모가 0 이하면 그 각으로는 목표 높이에 못 닿습니다(사거리·고도 밖).

| 거리 | 필요 속력 | 비행 시간 |
|---|---|---|
| 3 m | 5.5 m/s | 0.69 s |
| 9 m (궁수 사거리) | 9.4 m/s | 1.26 s |
| 49 m | 22 m/s (한계) | — |

`ProjectileSpeed`는 이제 **속력 한계 = 사거리 한계**입니다. 필요 속력이 이를 넘으면 쏘지 않습니다.

#### 조준 3단계

1. **예측 (반복 수렴)** — `TrySolveArcingIntercept`. 조준점 → 실제 비행 시간 → 다시 리드 를 2~3회 반복
2. **탄도** — `TrySolveArcingLaunch`. 위 식으로 속력과 비행 시간을 구함
3. **산포** — `ApplySpread`. **랭크에 반비례** (랭크1 9° → 랭크5 1.6°)

> **예측을 반복 수렴시키는 이유**: `TryPredictInterceptPoint`는 투사체가 **직선으로** 난다고 가정해 `거리/속력`으로 시간을 냅니다. 곡사는 실제 비행 시간이 훨씬 길어서 그대로 쓰면 시간을 크게 과소평가해 **항상 뒤를 쏩니다.** 9 m에서 1.26초면 그동안 대상이 4 m 넘게 이동하므로, 예측은 이제 선택이 아니라 필수입니다.

조사에서 확인한 **"명중이 들쭉날쭉하다 / 개별 표적보다 무리에게 더 정확하다"** 는 별도 규칙 없이 산포 하나에서 나옵니다. 한 명을 빗나간 화살이 옆의 적에게 맞기 때문입니다.

#### 방패는 맞은 방향으로 판정 · `Systems/Combat/ShieldSolver.cs`

정면(dot > 0.35) 또는 **위에서 내리꽂힘**이면 `ProjectileResistance`만큼 피해와 넉백이 함께 깎입니다. 조사의 **"측면에서 쏠 때 가장 잘 밀리고, 높은 곳에서 쏘면 가장 안 통한다"** 가 이 판정 하나에서 나옵니다.

#### 상방 기준선은 상수가 아니라 발사각에서 파생된다

곡사는 대칭 포물선이라 **평지에서는 발사각 = 하강각**입니다. 발사각 40°로 쏘면 평지 명중도 sin 40° ≈ 0.64로 기울어 떨어집니다. 그래서 상방 기준선은 반드시 발사각보다 위에 있어야 합니다. 아니면 **모든 화살이 항상 "위에서 온 것"으로 판정되어 방패병에게 화살이 통째로 무력해집니다.**

$$\text{threshold} = \sin(\theta_{\text{발사각}} + \theta_{\text{여유각}})$$

여유각은 `BattleTuning.ShieldSteepBlockMarginDegrees`(기본 11°)입니다. 40° + 11° = 51°, sin 51° ≈ 0.777.

> **예전에는 이 값이 `Arrow`의 `const 0.78f` 였습니다.** 발사각은 병과 에셋의 직렬화 필드인데 기준선은 코드 상수였으므로, 둘을 묶어 두는 것은 주석뿐이었습니다. 기획자가 인스펙터에서 발사각을 55°로 올리면 컴파일 오류도 런타임 경고도 없이 **방패병이 화살에 무적**이 됩니다. 겉으로는 아무 일도 일어나지 않아 §7.1과 같은 종류의, 가장 늦게 발견되는 고장입니다.
>
> 지금은 발사각이 `DamageInfo.ArcAngleDegrees`로 타격에 실려 오고, 기준선이 거기서 파생됩니다. **발사각을 바꾸면 기준선이 따라옵니다.** `ShieldSolverTests.발사각을_올려도_평지_사격은_상방으로_판정되지_않는다` 가 25°/40°/55°/70°에 대해 이 성질을 고정합니다.

#### 감쇠는 피격자가 단독으로 계산한다

무기는 **"무엇을 어느 방향으로 때렸는지"만** `DamageInfo`로 넘기고, 얼마나 막혔는지에는 관여하지 않습니다.

```csharp
victim.ReceiveHit(DamageInfo.Projectile(damage, direction, knockback, stagger, arcAngle, shooter));
```

> **예전에는** `TakeDamage(amount, source, isProjectile, alreadyMitigated)` 였습니다. 화살만 자기가 감쇠를 계산한 뒤 bool 인자로 "이미 깎았다"고 알렸습니다. 감쇠 규칙이 `Unit`과 `Arrow` 두 곳에 나뉘어 있었고, 피해·넉백·경직이 각각 별도 호출이라 **한 곳에만 감쇠를 곱하면 막아 낸 화살에 밀려나 익사**할 수 있었습니다. 지금은 규칙이 `Unit.ComputeMitigation` 한 곳에만 있고, 넉백·경직에 같은 계수가 자동으로 적용됩니다.

### 2.8 분대 점유 — 한 칸에 한 분대 · `Gameplay/Squads/SquadOccupancy.cs`

분대 둘이 같은 타일을 목적지로 삼으면 두 진형이 같은 중심을 공유합니다. 병사들이 뒤엉키고, 어느 분대가 어디 있는지 구분이 안 되며, 무엇보다 **"한 칸을 누가 지키는가"라는 이 게임의 기본 단위가 무너집니다.**

| 항목 | 규칙 |
|---|---|
| 점유 대상 | **목적지 타일**. 이동 중 스쳐 지나가는 것은 막지 않음 |
| 점유된 칸을 명령받으면 | 거절하지 않고 **BFS로 가장 가까운 빈 칸 보정** (반경 4칸) |
| 초기 배치 | 스폰 칸도 점유 |
| 분대 소멸 | 즉시 해제 (안 하면 죽은 분대가 칸을 영원히 막음) |

**이동 중 통과를 막지 않는 이유**는 두 가지입니다 — 물리적으로 자연스럽고, 막으면 좁은 길에서 분대가 영영 못 지나갑니다.

**거절 대신 보정하는 이유**는 한 칸 빗나간 클릭에 명령이 통째로 씹히면 조작이 고장 난 것처럼 느껴지기 때문입니다. BFS라 결과는 항상 원래 목적지에서 가장 가까운 칸이고, 통행 가능한 칸만 통과 경로로 쓰므로 바다 건너 반대편 해안 같은 엉뚱한 결과가 나오지 않습니다.

> **Rigidbody를 쓰지 않은 이유**: 화살은 작고 빠른 물체라 Rigidbody로는 프레임 사이를 건너뛰어 통과(터널링)합니다. 매 프레임 "직전 위치 → 현재 위치" 선분을 레이캐스트로 훑으면 아무리 빨라도 놓치지 않고, 충돌 대상도 마스크로 정확히 통제됩니다. 판정 자체는 실제 콜라이더에 대한 물리 질의입니다.

### 2.9 레이어

물리 전투를 넣으면서 유닛에 콜라이더가 생겼습니다. 레이어 분리가 필수가 됩니다.

| 레이어 | 용도 |
|---|---|
| `Terrain` (8) | 클릭 레이캐스트 대상 · 화살 충돌 |
| `Unit` (9) | 근접 무기 판정 대상 |
| `Projectile` (10) | 화살끼리 서로 무시 |

**마스크 없이 클릭 레이캐스트를 쏘면 병사 몸에 막혀 이동 명령이 통째로 씹힙니다.** 레이어는 `SRPG → 프로토타입 에셋 생성` 이 프로젝트 설정에 자동 등록합니다.

### 2.10 규모 대비 — 무엇이 먼저 무너지는가

유닛 수가 늘 때 제일 먼저 무너지는 것은 프레임당 호출 수가 아니라 **질의의 복잡도**입니다.

| 지점 | 이전 | 지금 |
|---|---|---|
| 이웃 질의 (`QueryTeam`) — 유닛마다 **매 프레임**, 조기 종료 없음 | O(N²) | 공간 색인 O(N·k) |
| 적 탐색 (`FindNearestEnemy`) — 표적이 없을 때마다 전수 조사 | O(N·M) | 공간 색인 O(N·k) |
| A\* 작업 배열 초기화 — 경로 길이와 무관 | O(격자)/회 | 세대 스탬프 O(방문 셀)/회 |
| 화살 생성 | 발당 `Instantiate`+`Destroy` | 풀 재사용 |
| 콜라이더 → `Unit` | `GetComponentInParent` (계층 순회) | `TryGetComponent` 우선 (§`UnitLookup`) |

> **MonoBehaviour `Update` 호출 수는 병목이 아닙니다.** 유닛 200 + 화살 200이면 약 400회이고, 한 번에 0.15µs 남짓이라 다 합쳐 0.06ms입니다. "Update를 매니저로 합쳐라"는 흔한 조언은 여기서 거의 효과가 없습니다. 실제 비용의 대부분은 위 표의 1~2번에 있었습니다.

#### 공간 색인 — `Systems/Spatial/SpatialGrid.cs`

전장이 섬 하나이고 크기가 생성 시점에 확정되므로 **해시가 아니라 조밀 배열**을 씁니다. 넓은 질의(궁수 교전 반경 10m)가 수십 개 셀을 훑는데, 해시라면 그만큼 해시 계산이 들지만 배열은 인덱스 산술뿐입니다.

- 셀 크기는 타일 크기를 그대로 씁니다. 분리 조향(반경 1m 미만)은 1~4개 셀만 봅니다.
- **위치를 함께 저장**하므로 결과가 정확합니다. 호출부가 거리를 다시 잴 필요가 없습니다.
- 프레임당 한 번 다시 만듭니다. 비우는 비용이 맵 크기가 아니라 **대상 수**에 비례하도록, 채워진 버킷만 기억해 둡니다.
- 갱신은 **첫 질의가 스스로** 합니다. 부트스트랩 `Update`에 두면 "유닛보다 먼저 돌아야 한다"는 숨은 조건이 생기고, 유니티의 스크립트 실행 순서는 정해져 있지 않으므로 그 조건은 언젠가 조용히 깨집니다.

한 프레임 스냅샷이라 색인 위치는 최대 한 프레임 낡습니다(60fps에서 6cm 남짓). `FindNearestEnemy`는 색인으로 후보만 좁히고 **순위는 최신 위치로** 정합니다.

#### A\* 세대 스탬프

예전에는 탐색마다 `gScore`·`cameFrom`·`closed` 세 배열을 셀 수만큼 초기화했습니다. **옆 칸으로 한 발짝 가는 경로에도** 64×64 격자면 12,288칸을 씁니다. 적 40명이 0.9초마다 경로를 다시 잡으면 이것만으로 초당 50만 칸입니다.

지금은 세대 번호만 올리고, 셀의 초기화는 **실제로 방문할 때** 일어납니다. 비용이 격자 크기가 아니라 탐색 범위에 비례합니다.

> 주의할 점이 하나 있습니다. 배열을 비우지 않으므로 **지난 탐색의 `cameFrom` 값이 그대로 남아 있습니다.** 경로를 되짚을 때 확인 없이 따라가면 옛 경로로 새어 나갑니다. `ReconstructPath`가 세대 스탬프를 확인하는 이유입니다. 이 실수는 예외를 내지 않고 "가끔 엉뚱한 경로"로만 나타납니다 — `많은_탐색을_반복해도_결과가_흔들리지_않는다` 와 `실패한_탐색_뒤에도_정상_경로를_찾는다` 가 이를 고정합니다.

#### 화살 풀 — `Gameplay/Weapons/ProjectilePool.cs`

궁수 100명이 1.4초 간격이면 초당 70발이고, 발마다 생성·파괴가 한 번씩 일어납니다. **GC가 정확히 가장 바쁜 순간에 돕니다.**

프리팹을 키로 나눠 담습니다. 키를 무시하면 궁수가 다른 병과의 투사체를 쏘는데, 그 증상은 한참 뒤에야 눈에 띕니다. 풀이 없어도 화살은 동작합니다 — 무기 하나를 떼어 시험할 때 풀까지 준비해야 한다면 그 자체가 결합입니다.

## 3. 어셈블리 경계가 지켜지는가

```
Common ← Data ← Framework ← Core ← Systems ← Gameplay ← UI ← Composition
```

**Systems는 Gameplay를 모릅니다.** 그래서 섬 생성·경로 탐색·진형·웨이브 타이밍을 GameObject 없이 EditMode에서 직접 테스트할 수 있습니다. 전투 AI가 핵심인 프로젝트에서 이 경계가 무너지면 AI를 자동 검증할 방법이 사라집니다.

경계 유지를 위해 한 가지 기법을 씁니다: **유닛 생성을 델리게이트로 주입**합니다.
`Squad`와 `EnemyShip`은 `Func<UnitDefinition, Team, bool, Vector3, Unit>`를 받아서 유닛을 만듭니다. 시각 표현 생성 방식(지금은 프리미티브, 나중엔 프리팹)이 바뀌어도 `BattleBootstrap.CreateUnit` 하나만 고치면 됩니다.

`넓은_격자에서도_힙이_넘치지_않는다` 는 실제로 잡은 버그를 고정한 테스트입니다. A*에 감소 키를 쓰지 않아 같은 셀이 힙에 여러 번 들어가는데, 힙을 셀 수만큼만 잡으면 64×64 격자에서 넘칩니다.

`발사각을_올려도_평지_사격은_상방으로_판정되지_않는다` 는 **테스트만이 유일한 방어선인** 종류를 고정합니다(§2.7). 컴파일러도 런타임도 잡지 못하고, 증상은 "방패병이 화살에 안 죽는다"로만 나타납니다. 25°/40°/55°/70° 네 발사각에 대해 성질을 못 박아 두면, 나중에 누가 기준선을 다시 상수로 되돌려도 즉시 빨간불이 켜집니다.

`질의_결과가_전수_조사와_정확히_같다` 는 최적화 검증의 기본형입니다. 공간 색인이 대체한 것은 **전수 조사**인데, 전수 조사는 느리지만 절대 틀리지 않습니다. 그러니 확인할 것은 속도가 아니라 **"빠른 답이 느린 답과 같은가"** 입니다. 무작위 배치와 무작위 질의를 여러 벌 만들어 두 방식을 직접 대조합니다.

> **EditMode 테스트에서 `Object.Destroy` 는 에러를 냅니다.** `Unit.Kill` 처럼 런타임에서 옳은 코드가 EditMode에서는 "Destroy may not be called from edit mode" 를 남기고, 예상하지 못한 에러 로그는 NUnit이 실패로 처리합니다. **프로덕션 코드를 테스트에 맞춰 비틀지 말고** 해당 테스트에서만 `LogAssert.ignoreFailingMessages` 로 그 잡음을 무시하십시오. 확인하려는 메시지가 따로 있다면 `LogAssert.Expect` 로 명시한 뒤 함께 씁니다.

### 4.2 PlayMode — 조립 검증 (`10.Tests/PlayMode/`)

단위 테스트가 각 시스템을 따로 본다면, 여기서는 부트스트랩이 그것들을 **실제로 엮어 내는지**를 봅니다.

| 테스트 | 검증 |
|---|---|
| 부트스트랩이 섬과 분대를 생성한다 | 컨텍스트·지형·상륙구역·유닛·지휘관 |
| 분대에 이동 명령을 내리면 앵커가 움직인다 | 명령 수락 → 경로 탐색 → 실제 이동 |
| 웨이브가 시작되면 적 상륙정과 병력이 생성된다 | 스케줄러 → 상륙정 → 하선 전 과정 |
| 지휘관이 죽으면 분대가 소멸한다 | 이중 손실 구조 |
| 선택 컨트롤러가 분대를 등록한다 | 조작 대상 연결 |

> **배치 모드 테스트 주의**: `-batchmode -nographics`에서는 프레임이 최대 속도로 돌아 `Time.deltaTime`이 0.0002초 수준입니다. "N프레임 기다린다"로 시간 경과를 가정하면 실제로는 몇 밀리초밖에 시뮬레이션되지 않습니다. 시간에 의존하는 PlayMode 테스트는 **프레임 수가 아니라 조건으로 대기**해야 합니다.

### 4.3 배치 모드에서 돌리기

```bash

Unity.exe -batchmode -nographics -projectPath <프로젝트> \

Unity.exe -batchmode -nographics -projectPath <프로젝트> \
```

## 7. 이미 밟은 함정

같은 실수를 반복하지 않도록 개발 중 실제로 겪은 것만 적습니다.

### 7.1 `AssetDatabase.StartAssetEditing()` 안에서 프리팹을 구우면 참조가 null이 된다

에셋 빌더를 `StartAssetEditing()` / `StopAssetEditing()` 으로 감싸 최적화했더니, **파일은 전부 생성됐는데 참조만 조용히 비었습니다.**

```yaml
# BattleSetup_Prototype.asset — 성공한 것처럼 보이지만 전부 null
EnemyShipPrefab: {fileID: 0}
SelectionMarkerPrefab: {fileID: 0}
OrderMarkerPrefab: {fileID: 0}
```

그 블록 안에서는 임포트가 지연되므로 `PrefabUtility.SaveAsPrefabAsset` 이 아직 에셋으로 등록되지 않은 객체를 돌려줍니다. 그걸 다른 에셋에 저장하면 `{fileID: 0}` 으로 직렬화됩니다.

**대응 세 가지**

1. 프리팹을 만드는 빌더는 `StartAssetEditing()` 으로 묶지 않는다
2. `SaveAsPrefabAsset` 의 반환값을 쓰지 말고, `ImportAsset(ForceSynchronousImport)` 후 **경로에서 다시 로드**한다 (`SavePrefab()` 헬퍼)
3. 빌더가 끝에 `VerifyReferences()` 로 **스스로 검사하고 에러를 낸다**

3번이 특히 중요합니다. 폴백이 있으면 참조가 끊겨도 게임이 그냥 돌아가서, 성공과 실패가 겉으로 구분되지 않습니다. 빌더가 소리를 내야 합니다.

### 7.2 배치 모드에서는 `Time.deltaTime` 이 0.0002초 수준이다

`-batchmode -nographics` 는 프레임을 최대 속도로 돌립니다. PlayMode 테스트에서 "30프레임 기다리면 시간이 흐르겠지"라고 가정했더니 실제로는 **5.8ms만 시뮬레이션**되어 이동 테스트가 실패했습니다.

시간에 의존하는 PlayMode 테스트는 **프레임 수가 아니라 조건으로 대기**해야 합니다.

```csharp
// 잘못 — 배치 모드에서 사실상 아무 시간도 흐르지 않음
for (int i = 0; i < 30; i++) yield return null;

// 올바름 — 조건 + 프레임 상한
while (frames < MaxFrames && moved <= Required) { yield return null; frames++; ... }
```

### 7.3 A* 에 감소 키가 없으면 힙이 셀 수보다 커진다

우선순위 큐에 decrease-key를 구현하지 않고 같은 셀을 여러 번 밀어 넣는 방식이라, 힙에는 셀 하나가 이웃 수(4)만큼 중복 적재될 수 있습니다. 힙 배열을 셀 수만큼만 잡으면 64×64 격자에서 `IndexOutOfRange` 가 납니다. `cellCount * 4 + 1` 로 잡았고 회귀 테스트를 붙였습니다.
